# Adding a language

Everything LocReminder says lives in **one file per language** under
`locale/`. To add Bangla:

```
cp locale/en.yaml locale/bn.yaml
```

Translate the text to the right of each colon, open a pull request, done. You
do not need Dart, Kotlin, Flutter, or any tooling. You do not have to
translate all of it: anything you leave out falls back to English, so a
half-finished translation still works and is still worth sending.

## Why one file, when the app reads three

Three different things render this app's text, and only one of them is
Flutter:

- The **app UI** is Flutter, and reads generated Dart.
- The **alarm** is deliberately *not* Flutter. It rings through a native
  Android Activity and notification so it still works when the Flutter engine
  is not running, which means its text has to be an Android string resource.
- The **store listing** is read by F-Droid straight from this repository, and
  never by the app at all.

A translator should not have to know any of that. So `locale/<code>.yaml`
holds all three, and `tool/gen_locale.py` splits it into the formats each
consumer needs:

```
locale/bn.yaml  ->  lib/l10n/strings.g.dart
                ->  android/app/src/main/res/values-bn/strings.xml
                ->  fastlane/metadata/android/bn/
```

## The generated files are committed, not built

`tool/gen_locale.py` never runs during a release build. Its output is checked
into the repository, and CI only verifies that the output still matches its
source (`python tool/gen_locale.py --check`). Edit a generated file by hand
and the build fails, telling you to regenerate.

This is deliberate, and it is the reason the whole thing carries no risk to
the reproducible build. F-Droid compiles this app itself and compares the
result to ours byte for byte; getting that working took six releases. Adding
a code generation step to that build would have put it back in play. Adding
files to a repository does not.

It is also why there is no `flutter_localizations` and no `intl` here. Those
are the standard answer, and they would have meant two more packages in a
dependency set CI installs with `--enforce-lockfile`, plus `gen-l10n` running
at build time. `Localizations` and `LocalizationsDelegate` are core Flutter,
so none of it was necessary.

**Maintainers:** after changing `locale/*.yaml`, run

```bash
python tool/gen_locale.py
```

or trigger the **Refresh generated strings** workflow, which does it and
commits the result.

## The file format

```yaml
meta:
  name: বাংলা          # what the language is called, in that language

alarm:                 # what the alarm says. Becomes an Android resource.
  alarm_stop_button: Stop alarm
  watch_armed:
    one: "{count} alarm armed"
    other: "{count} alarms armed"

store:                 # the F-Droid listing
  shortDescription: An alarm that rings when you arrive, not at a set time.

app:                   # the app's own screens
  addAlarm: Add alarm
```

**Curly braces** like `{place}` are filled in by the app at runtime. Keep
every one, spelled the same. You may move them around the sentence, which is
the point of having them — word order is not the same in every language.

**Plurals** are written as `one:` and `other:`. Languages that do not split
plurals the way English does can put the same text in both.

The generator refuses to run if a translation invents a key that does not
exist in `en.yaml`, or changes which placeholders a string uses. Both would
otherwise surface as a crash or a blank on someone's phone.

**Do not translate:** LocReminder, OpenStreetMap, OpenTopoMap, and the names
of phone makers and their software (Xiaomi, MIUI, HyperOS, Samsung, OnePlus).
Those appear in English on the phone itself, so translating them would send
people looking for a setting they cannot find.

## The full list of strings

`docs/LANGUAGE.md` is every word in the app in one place, generated by
`python tool/extract_strings.py`. It is meant to be filled in by hand and
then turned into a `locale/<code>.yaml`, so that contributing a language
needs no tooling at all.

Regenerate it after changing any user-facing text.

## Still to think about

**Decimal separators.** `formatDistance` writes `1.2 km`. Much of Europe
writes `1,2 km`. Without `intl` this needs a small locale-aware formatter, or
a `decimalSeparator` key in each language file.

**Right-to-left.** Not needed for Bangla. If Arabic or Urdu is ever added,
every hardcoded `EdgeInsets.only(left:)` becomes a bug, and they should be
`EdgeInsetsDirectional` instead. Cheap to do during the migration, expensive
to retrofit afterwards.

**Material's own widgets.** Date pickers and the like stay English without
`flutter_localizations`. This app barely uses them, so it has not been worth
the dependency — but that is the one thing that would justify adding it.
